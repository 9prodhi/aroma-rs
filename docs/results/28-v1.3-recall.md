# 28 — v1.3 (Aura + Visualforce) recall gate record (2026-11-20)

**Decision: the v1.3 recall gates do NOT pass, on the corpus floor.** The D46 recall
gates themselves hold on both seeds (Aura pooled start R@100 **0.9820**, VF pooled start
R@100 **1.0000**, each ≥ 0.98), and the Aura bundle floor passes (**397 ≥ 300**). The
Visualforce page floor fails: the pinned corpus yields **292** distinct indexed `.page`
files, **8 short** of the ≥ 300 floor. Because the shortfall is in the corpus, not the
recall, no sampling rule, threshold or search code was changed. The fix is to add more
`.page`-bearing public repositories (or drop the floor) — a corpus decision for the
release review.

the implementation available at that time.

## Why the VF page floor is short (primary miss cause)

- **The corpus holds only 295 distinct `.page` files** (raw file count across the 45 + 3
  repos) — below the 300 floor even before indexing. The shortfall is in the corpus, not
  the harness.
- **note 21 (internal research note, not published) overcounted.** Its scout line "Visualforce pages … total 335" counted
  `.page` **and** `.component` together (295 + 40 = 335). The D46 floor is specifically
  `.page` files ("VF pages"), and this task defines pages as distinct `.page` files with a
  Page unit, reporting `.component` separately.
- The indexer extracts **292** of the 295 raw `.page` files. The 3-file gap is the
  documented `tree-sitter-html` parse failure on inline-script / bare-`&` VF pages
  (note 20, internal research note, not published: 368/371 clean on the NPSP probe), not a floor that would otherwise have met 300.
- No repository is missing from the run: all 45 v1.3 repos were built (0 `files_failed`,
  0 `files_skipped_large`, 0 `units_skipped_damaged` across the run).
